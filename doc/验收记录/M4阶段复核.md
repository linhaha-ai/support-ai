## 已确认问题与后续处理

### M4-R01：向量发布测试夹具参数不匹配

[DocumentVectorDatabaseIT](../../backend/support-ai-bootstrap/src/test/java/com/haha/supportai/knowledge/document/DocumentVectorDatabaseIT.java) 的 `createFixture` 为 `document_version` 插入 SQL 提供 7 个参数，但语句只有 6 个占位符。本次 6 项测试均报“栏位索引超过许可范围：7，栏位数：6”，未进入向量写入、过期租约、完整性检查和 READY/active/SUCCEEDED 原子发布断言。

最小修复方向：按列核对夹具参数，统一文件哈希和配置哈希的取值，再单独重跑该类。此结果说明测试夹具有缺陷，不能直接判定生产发布逻辑失败，也不能声称该逻辑已通过数据库验证。

### M4-R02：现有开发库与合并后迁移序列不兼容（已解决）

2026-09-23 通过只读事务查询 `flyway_schema_history` 与 `to_regclass`，确认 `support-ai-dev-postgres-1` / `supportai` 当时的实际状态：

| 版本/对象 | 开发库已执行内容 | 2026-09-23 工作区要求 |
| --- | --- | --- |
| V1—V11 | 已登记成功，包含 `message_source` | 本次仅确认登记状态，未逐个复核历史校验和 |
| V12 | `create ticket` | `create_document_cleanup_job` |
| V13 | `create tool call and ticket source` | `create_ticket` |
| V14 | 无执行记录 | `create_tool_call_and_ticket_source` |
| `document_cleanup_job` | 不存在 | F19 删除清理所需 |
| `ticket`、`tool_call` | 均存在 | 已由旧序列创建，不能按空库流程重复创建 |

因此当时的问题不是“开发库仍停在 V10”或“只差执行 V14”，而是同一版本号对应的迁移内容发生变化。空库迁移成功不能证明旧数据卷可正常升级；该轮复核未启动后端重放 Flyway 校验，也未执行 `repair`、迁移、删表或重建数据卷。

2026-09-24 已采用前向兼容方案：恢复数据库已执行且校验值不可变的 V12 `create ticket`（`-706768438`）和 V13 `create tool call and ticket source`（`-1533669448`），将尚未执行的 `create document cleanup job` 顺延为 V14（`-326228586`）。没有执行 `repair`，也没有删表或重建数据卷。

新增 `FlywayMigrationCompatibilityIT` 先在临时 PostgreSQL 16/pgvector 数据库迁移到 V13，再加载当前迁移；结果为只执行一条 V14、14 个迁移全量校验成功、三个校验值保持预期，1/1 通过。随后实际启动后端，开发库从 V13 执行 V14，Spring Boot 在 8080 启动成功；只读复核确认 V12—V14 均成功登记，`document_cleanup_job` 存在。迁移兼容阻塞关闭，但 F19 的真实删除/发布竞争和页面场景仍待验收。
