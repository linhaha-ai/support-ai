## 本轮修正的遗漏

1. `chat_run.config_snapshot` 不再只保存 `mode`，而是记录实际 Chat/Embedding provider 与 model、1024 维、Prompt 版本、TopK、检索策略和 pgvector 索引信息；快照不含 API Key 等凭据。
2. F12 数据库集成测试不再依赖生产链路未使用的组合方法，改为先领取 RUNNING，再独立登记来源，并验证混合无效来源批次整体回滚和撤权后拒绝登记。
3. 回答完成后缓存的来源不能直接发送；sources 事件发出前重新按当前用户权限逐条核验，撤权或复核异常时返回空来源。
4. 每个问答任务从执行器接受时开始计算 180 秒总超时，包含排队时间；超时先保存 FAILED / `MODEL_TIMEOUT`，再中断任务。运行线程与超时线程竞争时沿用同一个稳定错误码。
5. 前端断流且首次状态查询失败时保留 active run、状态未知提示、刷新和可用的停止入口；活跃运行期间不能新建会话而丢失运行控制。
6. 文档已明确当前 M3 事件只有 `start/delta/sources/done/error`，`tool` 属于 F27 预留能力。

## M3 场景验收

1. 用户 A、用户 B 分别只在自己的固定知识范围创建会话并提问，检索、回答正文和来源互不越权。
2. 资料内问题按 start、delta、sources、done 完成，数据库正文与流中内容一致，全部入模证据均已登记，点击引用可定位原文。
3. 资料外问题不调用模型或不编造规则，保存明确的资料不足回答；未知引用编号不生成来源。
4. 检索后撤权、回答完成后撤权和来源点击前撤权均不能泄露来源；撤权后的会话拥有者仍可停止活跃运行。
5. 双击、幂等复用、同键不同载荷和同会话并行请求分别符合复用、冲突和单活跃约束，不产生重复模型调用。
6. SSE 断开后后台继续持久化，GET run 能恢复部分或完整结果；状态查询临时失败时页面仍能继续刷新或停止。
7. 正常完成、用户取消和 180 秒总超时同时竞争时只有一个终态，SSE 错误码与数据库一致。
8. 应用重启后遗留 QUEUED/RUNNING 只收口为 FAILED / `RUN_INTERRUPTED`，不会自动重放模型请求。
