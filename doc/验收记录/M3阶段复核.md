## 已确认问题与处理顺序

1. **M3-R01：批量来源登记 SQL 存在类型错误，优先修复。** [MessageSourceMapper](../../backend/support-ai-data/src/main/java/com/haha/supportai/data/conversation/mapper/MessageSourceMapper.java) 的 `insertAll` 使用 `UNION ALL`，`ticket_id`、`tool_call_id` 两列均为未显式指定类型的 `NULL`。本次数据库报 `ticket_id is of type uuid but expression is of type text`；只读 SQL 复核也确认这种联合查询把两列推断为 `text`。来源继承测试直接报错，混入越界来源的测试也提前报 SQL 异常，未到预期业务拒绝。最小修复方向是为这两列明确 UUID 类型，再验证两条以上来源的成功登记、整批回滚和根来源继承。不能以单元测试通过代替这条生产 SQL 验证。
2. **M3-R02：会话范围往返测试的排序口径不一致。** [ChatConversationMapperDatabaseIT](../../backend/support-ai-bootstrap/src/test/java/com/haha/supportai/conversation/ChatConversationMapperDatabaseIT.java) 使用随机 UUID 的 Java 自然序构造预期，生产查询使用数据库 `ORDER BY kb_id`；本轮两个 ID 的结果顺序与预期相反。需明确范围列表的排序契约，统一测试与实现口径，并用固定边界 ID 覆盖；当前失败不能直接推断为会话越权。
3. **M3-R03：OpenAPI 完整契约测试失败。** [OpenApiDocumentationTest](../../backend/support-ai-bootstrap/src/test/java/com/haha/supportai/config/OpenApiDocumentationTest.java) 中已认证 MockMvc 请求 `/v3/api-docs` 预期 200、实际 500，失败在完整路径断言之前。本次没有进一步确定生成异常根因，也没有用真实 HTTP 重放；需恢复文档生成后复核 F10—F20 路径、响应和安全要求。
4. **已解决的共同环境阻塞：开发库迁移历史不兼容。** 本次只读查询曾确认开发库已有 V12 `create ticket`、V13 `create tool call and ticket source`，且缺少 `document_cleanup_job`。2026-09-24 已保持这两个已执行迁移及校验值不变，将清理任务顺延为 V14；兼容回归、开发库实际升级、全量校验和后端启动均通过。详见 [M4 阶段复核](M4阶段复核.md) 的 M4-R02。

## 2026-09-21 历史复核

以下为上次交付记录，不是本次新增代码修复：当时前端 10 个文件、62/62 测试及生产构建通过；开发库当时只确认到 V10，后端测试、真实模型和完整场景未执行。本次结果见上文，旧测试数字不累加。

上次修正的遗漏：

1. `chat_run.config_snapshot` 不再只保存 `mode`，而是记录实际 Chat/Embedding provider 与 model、1024 维、Prompt 版本、TopK、检索策略和 pgvector 索引信息；快照不含 API Key 等凭据。
2. F12 数据库集成测试不再依赖生产链路未使用的组合方法，改为先领取 RUNNING，再独立登记来源，并验证混合无效来源批次整体回滚和撤权后拒绝登记。
3. 回答完成后缓存的来源不能直接发送；sources 事件发出前重新按当前用户权限逐条核验，撤权或复核异常时返回空来源。
4. 每个问答任务从执行器接受时开始计算 180 秒总超时，包含排队时间；超时先保存 FAILED / `MODEL_TIMEOUT`，再中断任务。运行线程与超时线程竞争时沿用同一个稳定错误码。
5. 前端断流且首次状态查询失败时保留 active run、状态未知提示、刷新和可用的停止入口；活跃运行期间不能新建会话而丢失运行控制。
6. 当时 M3 事件为 `start/delta/sources/done/error`，`tool` 为 F27 预留能力；本次只复核 RAG 路径，不据此认定当前 ASSISTANT 工具事件未实现。

## 尚待完成的 M3 场景验收

以下均需真实后端、真实模型和页面证据；已有单元或数据库覆盖的部分仍需串联验证。

1. 用户 A、用户 B 分别只在自己的固定知识范围创建会话并提问，检索、回答正文和来源互不越权。
2. 资料内问题按 start、delta、sources、done 完成，数据库正文与流中内容一致，全部入模证据均已登记，点击引用可定位原文。
3. 资料外问题不调用模型或不编造规则，保存明确的资料不足回答；未知引用编号不生成来源。
4. 检索后撤权、回答完成后撤权和来源点击前撤权均不能泄露来源；撤权后的会话拥有者仍可停止活跃运行。
5. 双击、幂等复用、同键不同载荷和同会话并行请求分别符合复用、冲突和单活跃约束，不产生重复模型调用。
6. SSE 断开后后台继续持久化，GET run 能恢复部分或完整结果；状态查询临时失败时页面仍能继续刷新或停止。
7. 正常完成、用户取消和 180 秒总超时同时竞争时只有一个终态，SSE 错误码与数据库一致。
8. 应用重启后遗留 QUEUED/RUNNING 只收口为 FAILED / `RUN_INTERRUPTED`，不会自动重放模型请求。

建议按“修复来源 SQL、排序断言和 OpenAPI 问题 → 重跑普通测试和相关数据库测试 → 真实模型/HTTP → 两用户页面场景”的顺序收口。场景记录应包含运行 ID、事件终态、消息正文一致性、来源版本和权限结果，不保存凭据。已知失败清零、上述场景通过且 F09 前置验收完成后，才可勾选 F10—F14 与 M3。
