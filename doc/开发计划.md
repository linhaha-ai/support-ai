# SupportAI 功能开发计划

项目版本：**V1.0.0**  
文档状态：阶段代码已整理，后端为 9 个 Maven 子模块；F02—F07 核心代码已实现，构建、真实应用 API 与运行回归待验收；F01 真实模型前置验收仍未完整通过。F03 的 V1—V5 SQL 已在一次性 pgvector PostgreSQL 容器验证，F05—F07 的迁移、MyBatis 映射、解析处理器和任务运行仍待后端验收；前端已有测试和生产构建结果不替代后端验收。结果见 [F01 验收记录](F01验收记录.md)、[F02 验收记录](F02验收记录.md)、[F03 验收记录](F03验收记录.md)、[F04 验收记录](F04验收记录.md)、[F05 验收记录](F05验收记录.md)、[F06 验收记录](F06验收记录.md) 和 [F07 验收记录](F07验收记录.md)。

SupportAI 面向研发和技术支持人员，提供知识库管理、文档问答、来源查看、会话管理和只读工单查询。以模拟订单系统的错误码、接口说明和故障处理资料作为业务样本。

本计划包含 **7 个累计里程碑、32 个小任务**。所有任务共同构成 V1.0.0；里程碑只表示功能逐步具备的状态。按编号推进，任务依赖列出的功能必须先通过验收。每完成一个任务，保留已经可用的业务能力，并执行受影响功能的回归检查。

技术基线为 JDK 21、Spring Boot 3.5.x、Spring AI Alibaba 1.1.2.2、配套 Spring AI 1.1.2、Sa-Token 1.46.0、PostgreSQL 16 + pgvector、Vue 3 + TypeScript。服务端采用模块化单体、Sa-Token Cookie 登录态 + Servlet Session CSRF、持久导入任务和 POST SSE；默认使用本机 Ollama 的 Chat 与 bge-m3 Embedding，支持独立切换北京地域 DashScope 的 Chat 与 text-embedding-v4 Embedding。两种向量模型均校验 1024 维，但必须使用各自独立的索引。精确补丁版本和依赖兼容性在环境任务中验证后锁定。

工程采用 common、data、storage、identity、ai、knowledge、conversation、assistant、bootstrap 九个子模块，由父工程统一管理版本。knowledge 内合并知识管理、导入与检索，assistant 内合并工单与 Agent；data 使用 MyBatis-Plus 3.5.17 的 Spring Boot 3 专用 Starter，统一维护数据库设施和 TypeHandler，并按业务分包承载实体 PO、持久化枚举、Repository 与 Mapper。data.knowledge 已落地知识库、成员、文档、版本和入库任务的数据对象与访问层；knowledge 已实现知识库、成员权限及文档上传受理，storage 已实现受控本地 `FileStore`。业务服务不直接使用 JdbcTemplate/RowMapper，业务授权和事务编排仍由所属业务服务决定，禁止跨域绕过服务直接调用 Repository/Mapper。bootstrap 是唯一启动入口，集中管理 Controller、应用配置、Flyway 迁移和集成验收。完整任务归属见[后端模块结构](后端模块结构.md)；MyBatis-Plus 映射及事务仍未执行 Maven 验证。

各阶段 Controller 统一归 support-ai-bootstrap 的 `com.haha.supportai.controller.<业务>`：认证和管理员账号目录位于 `controller.identity`，知识库、成员、文档上传和导入任务查询入口位于 `controller.knowledge`；会话和助手入口后续按需放入 `controller.conversation`、`controller.assistant`，不为规划功能创建空目录。其他代码先按业务模块归属，再按 `service / entity.dto / entity.vo / filter / handler / exception / config` 等职责分包；复杂功能可在职责包之前增加功能子包，不机械创建无实现的 service 接口。PO 集中在 data 对应业务域的 `entity.po`，DTO/VO、Service、安全配置、过滤器和异常处理器继续留在原业务模块。纯单元测试跟随被测类包结构，控制器与跨模块集成测试保留在 bootstrap。九个子模块不变；底层 JDBC 仍由 MyBatis-Plus、PgVectorStore 及独立 SQL 验收夹具使用。数据库映射、回滚、租约并发、解析分块和依赖版本的运行验证待执行，F01—F07 验收状态保持未勾选。

## 执行规则

- 完成标识：`- [ ]` 表示未完成，验收通过后改为 `- [x]`；阶段勾选以本阶段全部任务和完成检查通过为准。
- 每个任务完成后，都要能够通过页面操作、接口调用或针对性自动化测试复现验收结果。涉及真实模型的验证显式执行，不把模拟结果当作模型接入成功。
- 数据库迁移、服务端用例、接口 DTO、前端状态和必要测试随业务任务一起提交；数据库结构改变时同步更新查询与结果映射。
- 权限、当前文档版本、运行状态和来源记录属于业务功能的组成部分，随首次提供该能力一起实现。
- 新功能尚未通过验收时，对应入口保持不可用；失败、取消和资料不足必须在界面上有明确反馈。
- 同一任务中先做最小可用行为，再补异常分支；只增加完成该业务所需的组件。

### F02 用户登录、退出和身份状态

- [ ] 已完成并通过验收（F02）

- **依赖：** F01。
- **实现内容：** 使用 Flyway 建立 `app_user`，V4 自动补齐默认管理员 `admin/admin`。独立 SQL `backend/support-ai-data/src/main/resources/db/seed/identity/init_app_user.sql` 保留管理员及 `support1/support1`、`support2/support2` 两位普通演示用户，供按需手动补齐。两份脚本保存兼容 jBCrypt 的 cost 12 BCrypt 摘要，通过 `ON CONFLICT (username) DO NOTHING` 仅补齐缺失账号，不覆盖已有密码、角色或状态；不恢复 Java 建用户逻辑。完成登录页及 `GET /api/auth/csrf`、`POST /api/auth/login`、`POST /api/auth/logout`、`GET /api/auth/me`。权限框架使用 Sa-Token 1.46.0，采用 HttpOnly Cookie 传递登录 token；登录成功签发不可复用的新 token，并轮换用于 CSRF 的 Servlet Session，统一返回脱敏错误响应。使用 springdoc-openapi 2.9.1 生成 OpenAPI 3.0 契约，并用 Knife4j 4.5.0 提供受登录保护的接口文档页面。
- **验收：** 正确账号能登录并取得新的 Sa-Token Cookie，再次登录后旧 token 失效；错误密码不能登录；未登录访问业务接口、Actuator 子端点和接口文档返回 401；缺失或错误 CSRF 的写请求返回 403；退出后原 Sa-Token 和 CSRF Session 均无效。停用账号不能继续访问受保护接口，接口与日志均不出现密码、密码摘要、token 或密钥。OpenAPI JSON 必须包含全部已实现接口、请求模型、成功响应模型与状态、CSRF 请求头和 Cookie 鉴权方案，Actuator 健康接口进入独立分组。成功响应从返回类型和 HTTP 状态注解生成，不要求每个接口重复枚举通用错误响应；实际错误状态与结构通过安全回归验证。
- **新增能力：** 用户可以以自己的身份进入和退出系统。
- **阶段交付：** 已实现账号表、V4 默认管理员初始化与可选手动种子 SQL、四个认证接口、Sa-Token Cookie 与 CSRF、停用检查和脱敏错误、登录与状态页面、受保护的 OpenAPI/Knife4j 文档；配套完成九模块组织、Controller 归 bootstrap、MyBatis-Plus 数据访问和自动化测试代码。V3 补齐 app_user 表及全部 8 列中文注释，既有迁移内容保留。2026-09-21 已在当前开发库直接执行 V4 文件，确认管理员已补齐且启用，幂等重放未新增记录，`admin/admin` 基础登录通过；Flyway V4 历史登记待下次正常启动。此前前端 19 项 mock fetch 测试与生产构建通过，后端构建与完整认证回归仍待验收。

### F04 成员授权、撤权和读写边界

- [ ] 已完成并通过验收（F04）

- **依赖：** F03。
- **实现内容：** 完成成员管理页、`GET /api/admin/users`、成员列表 GET 和成员关系 PUT/DELETE；实现共享授权组件。READ 允许查阅和问答，WRITE 额外允许文档维护。ADMIN 的管理能力与资料读取权分别判断；负责人字段不绕过成员校验。

- **阶段交付：** 已实现不含密码字段的管理员账号目录、成员列表、幂等授权/改权、幂等撤权 4 个接口及知识库成员管理界面。`AccessPolicy` 统一提供 ADMIN、KB-R、KB-W 校验；普通数据访问将知识库不存在、停用和无成员权统一处理为 404，管理能力不替代成员读取权。成员复合主键写入使用 PostgreSQL `ON CONFLICT`，保留首次授权时间并记录最近授权人。前端 3 个测试文件共 26 项测试和生产构建已通过；后端单元、OpenAPI 和真实 PostgreSQL 集成测试代码已补齐，但按仓库规则未运行 Maven，真实 API、三账号切换和浏览器视觉验收仍待执行，因此 F04 保持未勾选。

### F06 查看持久处理任务并可靠领取任务

- [ ] 已完成并通过验收（F06）

- **依赖：** F05。
- **实现内容：** 实现 `GET /api/ingestion-jobs/{jobId}` 和任务状态展示；建设有界 Worker、任务领取、attempt、租约 token、进度和脱敏错误。任务阶段可分别展示解析、分块、向量化和发布。事务只保护领取和状态写入，外部调用不占用数据库事务。
- **验收：** 重复触发领取时，一个任务只有一个有效执行者；未完成全部阶段不能进入 SUCCEEDED。执行权失效的 Worker 不能提交阶段结果，重启后任务记录仍在。篡改 jobId 不能查看其他知识库任务，页面能区分排队、运行和失败。
- **新增能力：** 用户能看到文档的处理位置与结果，处理过程有持久记录。
